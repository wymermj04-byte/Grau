# GRAU

GRAU is a BJJ gym command center for running classes, managing members, tracking attendance, and keeping an eye on membership revenue.

Coach access is protected by Supabase email/password authentication. Sessions persist through the app’s shared auth provider and refresh automatically; users who are signed out see the Sign In screen, and Settings includes Logout. Supabase invitation and recovery links open the dedicated password-setup route, which exchanges a PKCE code or implicit-session fragment without logging credentials, then lets that authenticated user choose a password. It never creates a user or assigns a staff role; administrators must assign the `gym_staff` membership before inviting a coach. The root navigator uses Expo Router `Stack.Protected` guards rather than a root-level redirect, so a protected screen cannot mount before authentication and navigation-state updates cannot loop. Staff database operations go through the shared authenticated Supabase data layer, which requires a current session and exactly one active `gym_staff` membership, scopes every query to that gym, checks selected students belong to it before attendance, payment, or promotion writes, and discards in-flight results after logout. Accounts with no staff membership may instead open the separate **My family** experience only when the deployed `my_linked_members()` RPC returns an approved link; its member detail reads attendance only through the deployed `my_linked_member_attendance(student_id)` RPC and clears data when the approved link or account changes. It never grants roster, Finance, payment, or staff access. Accounts with neither access path see contact-your-gym guidance. There is never a default gym. Coach accounts are created administratively—there is no public registration flow.

Family Messaging screens and their typed `family_staff_*` RPC client are present but fail closed behind a disabled local capability switch. While disabled, the screens make no messaging RPC calls and navigation stays hidden. Composer state is persisted only after the server-authorized conversation resolves its exact user, role, gym, and conversation scope; secure Expo Crypto retry UUIDs are written before sends, reused for an unchanged unknown outcome, and never replaced by edits. Ordered local writes keep unresolved attempts separate, and cleanup failures block further sends until safely reconciled. Secure UUID generation and storage both fail closed. A separately gated, development-only inbox diagnostic emits only safe aggregate results and can call only the two read-only inbox RPCs after deliberate user action. The separate `messagingControlledTestCapability` is development-only and currently enabled solely for approved Gym 4 controlled-test preparation; it persists only a safe run ID, server IDs, fixed test text, retry UUIDs, read cursors, and up to eight aggregate family-inbox diagnostics locally across account switches. Failed acknowledgements retain safe conversation/cursor/role/endpoint context and show the server error code and safe message, while the run stays halted. The separate `messagingControlledAcknowledgementRecoveryCapability` is enabled only for the approved development-only availability check and is limited to the exact halted Gym 4 family run with Conversation 1 and Messages 1 and 2; only after a further explicit confirmation does it recheck family authorization, request and validate one fresh cursor without acknowledging it, and preserve the original cursor for diagnostics. `messagingControlledCompletionCapability` is development-only and enabled only for the approved completion-interface check: it is limited to that same exact halted run with recovered endpoint 2, and only after a further explicit confirmation performs one fresh family-authorized inbox read, requires Conversation 1 at Gym 4 with aggregate unread count zero, and then enables only the opposite-role-denial check. It cannot send, acknowledge, create or replace a cursor, or change a read marker. Restoration, rendering, and error handling can never issue or replace an unread cursor. A halted run, or an interrupted preflight checkpoint that has no conversation, messages, pending sends, or cursor, can recover only through a manually entered conversation ID and a confirmed, family-scoped inbox plus empty-history check; it never creates a replacement conversation or UUID. Normal Family Messaging remains disabled.

The Gym 4-only server rollout remains review-only. Its deployment manifest contains the approved read-only Main inventory for all sixteen Phase 1 routine definitions plus raw-ACL/default-ACL hashes, rejects unexpected messaging overloads, uses a private backup schema with no API-role access, retains the function and private-helper rollback contract after rollback, and never enables normal messaging by itself. Production Messaging stays disabled until disposable validation, server rollout, durable retry persistence, navigation, and remaining authorization tests are complete.

Family Self-Check-In is implemented locally but remains disabled. Its guarded routes and typed RPC client cannot call a self-check-in function while the local capability is off. Gym 4 has one reusable academy QR destination (`/check-in/4`), shown only in a staff development print preview; it contains no class, student, attendance, or authorization data. The scan gateway requires sign-in and approved family access, and it remains unavailable until the same local capability is enabled. The deployed migration in `docs/family-self-check-in-migration.sql` creates private request/audit objects, leaves the Gym 4 rollout absent, and makes staff approval—not family request—the sole attendance path. When enabled later, family requests and staff resolutions retain an account-scoped exact-payload retry UUID; staff resolutions require explicit confirmation and refresh their request and attendance state after successful approval. A separate disabled development-only authorization diagnostic may make one deliberate fail-closed RPC probe at a time for approved Gym 4 family accounts or active Gym 4 staff; it never displays returned records and must not enable operational self-check-in. The development-only pilot-readiness route supports an active Gym 4 admin/coach’s selected class, student, attendance, and advancement snapshot check, plus an approved family’s own authorized-link and rollout-disabled check; every probe is deliberate and aggregate-only. Deployment revision and trigger/index integrity remain explicit manual confirmations.

Promotion Notifications has a deployed private Main Supabase foundation and official promotion enqueue integration, but Gym 4 remains disabled on the server. The normal production notification route additionally requires an authenticated approved Gym 4 family account; the server rollout gate remains authoritative, so its disabled response displays a temporarily-unavailable state without inbox data or an unread badge. The family dashboard uses one unified bell for enabled, authorized message and promotion categories, without acknowledging anything when the center opens. Message items open their authorized conversations; unread promotion items acknowledge through the approved RPC before opening the preserved promotion inbox. Promotion entries can safely use the already-authorized linked student’s name, but retain generic celebration wording because the public inbox contract does not expose the historical promotion rank or stripe snapshot. The client never reads private notification tables or embeds a service-role credential. A separate development-only family diagnostic is protected by an approved Gym 4 family link and can make one deliberate `family_promotion_notification_inbox(50)` call, reporting only its authorized response or a sanitized server denial; it cannot change notification state or bypass the rollout gate. The server worker is a Supabase Edge Function that uses secret-key authentication and returns a safe no-op while disabled. An approved external scheduler is still required because the project has no database scheduler.

A separate development-only Gym 4 administrator controlled-test screen can read the fixed notification-test student and its exact approved family link. Only the White 0 to White 1 test promotion is enabled, and it uses `record_student_promotion` after an explicit confirmation plus a fresh exact-precondition reload. Trusted server rollout activation and secret-authenticated worker execution remain disabled. Private notification artifacts remain verifiable only through reviewed aggregate SQL and the separate approved family login.

The development-only Gym 4 notification-test family-link approval utility is enabled only for the approved controlled test and remains hidden from normal navigation. It requires an authenticated active Gym 4 administrator and an explicit confirmation, and uses only the reviewed `approve_member_account_link` RPC for the fixed Student 64 test target. Its persisted secure request UUID is scoped to the administrator and target for safe retries; it never writes the link table directly or enables promotion notifications.

## What is in this first version

- Today dashboard with the next class, arrival activity, and gym health signals
- Class schedule with selectable days and capacity tracking
- Member directory with search and member-state filters
- Live member profile reached from each directory row
- Check-in roster where attendance can be toggled during a session
- Finance overview with recent membership activity and collections summary
- Promotion review list that surfaces only members whose saved class requirement is met

## Data

Members, Schedule, Today, Attendance Reports, Finance, and Check-in load live authenticated Supabase records scoped to the signed-in coach’s active gym. Before any protected screen mounts, the app verifies exactly one active `gym_staff` membership; accounts without one see “No gym access—contact your administrator,” and no protected data or actions are rendered. A membership lookup failure is shown as a separate temporary access-verification error. Both blocked states include Sign out and switch account, which clears the session and returns to Sign In. Today greets the signed-in coach from existing Supabase user metadata only: `preferred_title`/`title` plus `display_name`/`full_name` when present, otherwise “Coach”; it never derives a name from an email. Finance calculates current-month collected revenue from paid payments, outstanding balances from pending/late/overdue payments, payment completion, recorded-month totals, and newest-first activity from the returned payment list; an empty response shows zeroes and no transactions, while a load failure shows an error instead of sample figures. Member search and filters run against live students; the saved `students.programs` array supports independent Kids and Adults assignments, including both programs. The directory’s All/Kids/Adults selector combines with name search and keeps unassigned members under All only. Schedule keeps a local-date week navigator with Previous Week, Next Week, and Today controls while showing each selected calendar day’s live class records in chronological order. Check-in opens only a real in-progress class roster and otherwise shows a no-active-class state. Today refreshes on focus and calculates active members, classes scheduled today, classes in progress, the next scheduled class, today’s attendance, and paid-this-month revenue. Attendance Reports is reachable from Today’s attendance section, refreshes on focus, joins attendance to live students and classes, and offers Today, Last 7 days, and All time views ordered newest-first. Protected data screens show loading, error, or successful-empty states; they never substitute sample records.

Billing is a read-only, administrator-only screen linked from Finance. It reads authenticated, gym-scoped billing profiles, charges, allocations, guardian contacts, billing settings, and members through the shared data layer. It calculates charge balances in integer cents and uses the configured gym timezone for Paid, Upcoming, and Due labels. Until the billing migration is deployed to the connected Supabase project, it clearly reports that billing is not enabled rather than showing zeroes or demo data.

Scheduled live classes open a coach roster. Starting a class updates its live `is_active` and `status`; coach check-ins use the current numeric class ID and class name, the live class `gym_id`, and only admit students whose live `gym_id` matches. When the scheduled-class attendance unique index returns PostgreSQL `23505`, the roster performs one authenticated, gym-scoped read for that exact class/student pair: a matching saved row displays Checked in and “Already checked in,” while a failed or empty read remains an error. It never retries the insert or uses upsert. Member-profile Open Mat check-ins load the selected live student, send that student’s valid `gym_id`, and explicitly send a nullable class ID because they are not tied to a scheduled class and remain outside this index protection. Both flows block with a clear message when their live gym association is missing or inconsistent. Create Attendance is Runtime Ready following a 201 verification; its response uses numeric student, class, and gym IDs, while the existing List Attendance metadata preserves nullable Open Mat class IDs. Ending the class updates its status to Completed and returns to the refreshed Schedule.

List Class Attendance is configured as an untested `GET /attendance` endpoint in the existing Supabase REST service. It returns only student, class, and gym IDs filtered by required class and gym values; no screen uses it yet.

An isolated, apikey-only Supabase Class Attendance service also has an untested List Class Attendance `GET /attendance` endpoint with the same class and gym filters. It has no Authorization header and is not yet used by a screen.

Schedule also includes a Create Class form. It resolves the live gym ID only when exactly one Gym Settings record is returned, validates the required details, Kids/Adults/Mixed audience, and later end time, then creates a class with the existing `Fundamentals` type, its saved audience, a `Scheduled` / inactive initial state, and that resolved ID. Scheduled classes expose Edit Class through the existing authenticated, gym-scoped update helper; active admins and coaches may edit them. Active admins may also correct a Completed class while its status stays Completed. Completed-class attendance has a separate admin/coach correction mode: staff can add a missed check-in or explicitly confirm removal of one saved check-in, without reopening the class or rewriting other attendance. The editor updates the same class ID only, preserves attendance, and requires confirmation after checking saved attendance when date, start time, or stripe-progress classification changes. In Progress and Cancelled classes remain read-only outside the established Start/End workflow. Live class rosters use the saved audience against each student’s saved program assignments while retaining any already checked-in student; legacy classes with no audience retain their full roster, while completed attendance remains unfiltered. Saved roster attendance is read with a gym- and class-scoped, ordered paginated query, so unrelated gym history cannot replace current-class check-in state. It prevents duplicate submissions, retains entries on failure, and returns to the refreshed Schedule after success.

Each member row opens a profile using that student’s `studentId`. The profile reloads and matches the live student record before displaying rank, stripes, membership, waiver status, and an optional photo. Current Rank uses a shared adult/youth belt palette, including two-color youth ranks; unknown saved ranks use a neutral themed card without changing member data.

The supplied Sandusky Bay waiver is preserved exactly in `docs/waiver-signing-review.md`. Member profiles now include a staff-assisted **Sign current waiver** route. It checks the authenticated gym’s approved waiver version before showing a signature form; while the private bucket and migration are absent, it shows a clear unavailable state and cannot collect or save a signature. The unexecuted read-only inventory, migration, and staging-only verification plan are in `docs/waiver-supabase-inventory.sql`, `docs/waiver-supabase-migration.sql`, and `docs/waiver-staging-tests.sql`. The migration creates private, append-only digital submissions and server-side finalization; it must be reviewed and deployed before signing can be enabled.

In development previews only, Settings includes **Signature pad test**. It renders the same pad used by waiver signing, supports drawing, Clear, and Back, and has no save action or Supabase, Storage, or finalization calls. It is unavailable from production navigation. The pad copies touch coordinates synchronously before deferred state updates, ignores unavailable/cancelled event data, clamps positions to its measured bounds, keeps the CSS Interop pseudo-style and drawing-surface structure stable from first render, and disables only its parent scroll view for the active drawing gesture. `scripts/check-signature-pad.cjs` provides the focused mocked regression check for those cases.

Member profiles keep the selected `studentId` through every action. Payment History, Check In, Attendance History, Promote Student, Add Payment, and Edit Member are connected.

Members has an Add Student form backed by the verified Create student endpoint. It trims names, requires a first name, and sends the live, screen-resolved gym ID only when exactly one Gym Settings record is returned; it never hardcodes a gym. Blank photo URLs are sent in the existing supported string format. The screen blocks duplicate saves, retains values and shows useful errors on failure, then returns to a refreshed Members list after success.

Check In is the exception: it records a real Open Mat attendance row through the verified Supabase Reset endpoint using the selected student ID and the current timestamp. The screen disables repeat submits while the request runs and after success.

Stripe progress is progressively enabled: when the connected gym has both the base stripe-progress schema and the historical-date amendment, member profiles reload progress when focused and count only the selected member’s distinct scheduled classes whose immutable attendance snapshot is `qualifying`. They show the configured requirement and remaining classes, and offer a staff-confirmed Historical Promotion Setup panel plus a separate confirmed baseline form for incomplete history. The panel uses a cross-platform calendar picker and the authenticated `confirm_student_historical_promotion_date` RPC only; it records a confirmation without changing rank, attendance, promotion rows, or baselines. App-recorded promotion timestamps take precedence, then the newest matching historical correction, then matching baselines; sources and counts are never combined. The reader accepts the existing class contract—UTC-midnight calendar `class_date` plus separate local `start_time`—and reports nonconforming records without backfilling or guessing. Open Mat and unclassified attendance remain visible in history but do not count. Members need an explicitly saved Kids or Adults promotion track, selected by staff; it is independent from the classes/programs the member attends, and progress never infers a track or historical count. At four stripes the app reports that belt requirements are not configured. The calendar sends unchanged `YYYY-MM-DD` values to the RPC. If the connected gym does not yet have the amendment, these surfaces clearly report “Stripe progress is not enabled yet” and existing member, attendance, class, and promotion workflows remain available.

Promote Student runs a read-only schema capability check before saving. Only a database-declared absence of the dedicated stripe baseline table permits the legacy promotion flow. When the stripe schema is present, it uses the atomic `record_student_promotion` RPC; a missing RPC, permission, network, validation, or internal RPC failure remains an error and never triggers a legacy write.

Add Payment records a live member payment with amount, a method choice, status, type, and optional notes. Non-Membership payments retain the existing live payment workflow. Membership payments require Paid status, a dues month, and an eligible individual or family tracking account; an active admin submits them through the atomic authenticated payment-tracking RPC, so the payment and its dues-month link succeed or fail together. The screen never creates tracking accounts or uses a separate create-then-link path, reuses the same UUID on retries, and blocks duplicate submissions. Its confirmation links straight to the member’s live Payment History.

Monthly Payment Tracking is separate from Add Payment. Active administrators can review one existing, gym-scoped payment inside the selected account-month, then explicitly confirm a link through the authenticated payment-tracking RPC. The link flow reuses its idempotency key on retries, never calls the new-payment operation, and refreshes tracking after the server confirms the original payment and account-month IDs.

Attendance History also uses live Supabase data. It shows only the selected member’s attendance rows, ordered newest-first, including the check-in date/time, class type, and non-empty notes.

Financial Reports is available from Finance and uses live Payments and Students records. It provides date filters, paid revenue (paid payments only), pending and late/overdue totals, recorded totals grouped by payment method, and newest-first transactions matched to members. It does not create, change, or infer payment records.

Settings is available from Finance. Its Gym Information screen loads the single live gym-settings record, pre-fills the supported name, contact, website, and logo fields, and updates that same record using its loaded ID. If multiple gym records are returned, editing is blocked until authenticated gym selection is available.

Payment History uses live Supabase data too. It filters payments by the selected member, orders records newest-first, and shows the recorded amount, method, status, type, date/time, and non-empty notes.

Edit Member pre-fills the live member record and updates rank and saved program details. Where the new column is available, it also requires staff to choose a saved Kids or Adults promotion track; it does not need to match an assigned program, and no track is inferred.

The Promotion board uses saved progress data to provide a coach review list labelled “Class requirement met.” It does not award stripes or belts automatically.

## Stack

Expo Router, React Native, NativeWind, and the existing Draftbit component primitives. Appearance defaults to System and can be changed to Light or Dark in Settings; the preference is stored locally. Shared GRAU semantic theme tokens drive navigation, cards, inputs, dialogs, text, icons, loading indicators, and status states: Dark uses `#171B1A` with `#29302C` surfaces, while Light uses `#F3F0E8` with `#E4E5DF` surfaces; both use the accessible `#A63832` accent. The shared header links to Settings and displays saved coach initials (or a person icon when no saved profile name is available); Settings replaces that self-link with a visible Back button that returns through history or replaces a direct link with the Today dashboard. `PageContent` keeps protected screens centered with a readable desktop maximum while retaining phone-safe horizontal padding; cards wrap rather than overflow, and the Classes week selector now fits all seven days in the available phone width. Sign in selects the bundled charcoal GRAU logo on Light and ivory-on-charcoal GRAU logo on Dark (including System's resolved appearance), uses `resizeMode="contain"`, presents the uppercase product tagline as live text, and scrolls safely above the keyboard on compact devices.
